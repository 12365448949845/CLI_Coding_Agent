# Spec 驱动开发

把用户的想法变成可运行、可验收的代码，中间必须经过四份递进文档：

```text
spec.md（做什么） -> plan.md（怎么做） -> task.md（按什么顺序做） -> checklist.md（做对了没）
```

每份文档都在前一份的基础上细化。每个阶段都要得到用户明确批准后，才能进入下一阶段。

## 硬性门控

四份文档全部生成并获得用户批准之前，禁止编写、修改或生成任何实现代码。无论项目多简单，都必须走完四个阶段；简单项目可以让文档很短，但不能省略文件或审批。

允许在门控期间阅读代码、文档、配置和提交记录，也允许创建或修改这四份规划文档。不要因为需求看起来明确、只涉及一个函数或只改一个配置项而跳过流程。

## 总体流程

```text
用户想法
    |
    v
阶段一：需求澄清 -> spec.md -> 用户明确批准？
    | 未批准：修改并重新审批
    v
阶段二：技术设计 -> plan.md -> 用户明确批准？
    | 未批准：修改并重新审批
    v
阶段三：任务拆解 -> task.md -> 用户明确批准？
    | 未批准：修改并重新审批
    v
阶段四：验收设计 -> checklist.md -> 用户明确批准？
    | 未批准：修改并重新审批
    v
阶段五：开发（严格按 task.md）
    v
阶段六：验收（严格按 checklist.md）
```

### 审批规则

- 一次只问一个澄清问题；能用选择题就优先使用选择题。
- 对每份文档逐段呈现，并等待用户确认当前段落后再呈现下一段。
- 一份文档所有段落完成后，再请求整份文档的明确批准。
- 只有用户明确说“批准”“通过”“确认”或等价表达时，才把阶段标记为已批准。沉默、继续讨论或“看起来可以”不算批准。
- 用户要求修改时，只修改受影响内容，重新执行相关自检并重新请求该份文档的批准。
- 后一份文档不得在前一份文档获批前开始生成；实现代码不得在四份文档全部获批前出现。
- 如果需求包含多个独立子系统，先指出拆分边界并与用户确认拆分，再分别建立范围清晰的项目；不要把互不相关的工作塞进同一轮流程。

## 阶段一：需求澄清 -> `spec.md`

### 进入阶段前

先阅读现有代码、文档、配置和最近的提交记录，确认当前状态、已有能力、本次新增行为以及可能影响的边界。此阶段只做理解和规划，不改实现代码。

### 澄清顺序

逐个询问以下信息，每轮只问一个问题：

1. 目的和动机：要解决什么问题，谁会使用？
2. 成功标准：完成后怎样判断结果正确？
3. 功能边界：必须支持什么，明确不做什么？
4. 约束：性能、兼容性、安全性、数据、部署或时间约束是什么？

信息已足够时，提出 2-3 种可行方案，第一项放推荐方案，并说明每项的主要优点、代价和适用条件。让用户选择或确认推荐方案后再起草文档。

### 逐段呈现顺序

按下面的顺序逐段展示，每段等待用户确认：

1. 背景与目标
2. 功能需求（`F1`、`F2`……）
3. 非功能需求（`N1`、`N2`……）
4. 不做的事
5. 验收标准（`AC1`、`AC2`……）

### `spec.md` 模板

```markdown
# [标题] Spec

## 背景
（要解决什么问题，当前已有什么）

## 目标
- ...

## 功能需求
- F1: ...
- F2: ...

## 非功能需求
- N1: ...

## 不做的事
- ...

## 验收标准
- AC1: ...
- AC2: ...
```

### 写作与自检

- 聚焦用户可观察的行为，例如“提供一个主入口，接收环境上下文和可选配置，输出完整的 System Prompt 文本”，不要在 spec 中写函数名、类名、方法签名或具体数据结构。
- 保持语言和实现无关；具体语言、接口、类型和文件路径留给后续文档。
- 范围应能在一个实现周期内完成；未来可能做但本轮不做的内容写入“不做的事”。
- 每条功能需求至少对应一条验收标准。
- 提交审批前逐项检查：没有 `TBD`、`TODO` 或未完成小节；没有语言泄漏；没有可产生两种解释的歧义；范围明确；验收标准可运行或观察验证。

### 审批提示

```text
spec.md 已生成。请 review：
- 功能需求是否完整？
- 有没有遗漏的边界情况？
- “不做的事”是否合理？
- 验收标准是否可观测？

确认后进入技术设计阶段。
```

等待明确批准后才能进入阶段二。

## 阶段二：技术设计 -> `plan.md`

### 流程

重新阅读已批准的 `spec.md`，设计满足所有需求的架构，定义核心数据结构和接口，说明模块交互与数据流，记录关键技术决策及理由。使用用户已选语言和项目已有技术栈；若语言或技术栈仍未知，先询问一个问题，不要擅自假设会改变实现方向的选择。

按下面的顺序逐段展示并逐段等待确认：架构概览、核心数据结构、接口、模块设计、模块交互、文件组织、技术决策。完成后运行自检并请求整份 `plan.md` 审批。

### `plan.md` 模板

```markdown
# [标题] Plan

## 架构概览
（组件/模块划分，每个组件一段话）

## 核心数据结构

### [结构体名]
（字段定义及说明）

### [接口名]
（方法签名及用途）

## 模块设计

### [模块 A]
**职责：** ...
**对外接口：** ...
**依赖：** ...

### [模块 B]
...

## 模块交互
（调用链、数据流、调用顺序）

## 文件组织
（目录和文件级别的组织）

## 技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| ... | ... | ... |
```

### 写作与自检

- `plan.md` 可以且必须与语言、框架和项目结构相关。
- `spec.md` 的每条 `F` 需求都要有明确的架构或模块归属；列出并补齐任何缺口。
- 光看接口描述，应能独立实现每个模块；模块依赖必须明确且无循环。
- 文件组织写到目录和文件级别，但不要把易过期的行号写入计划。
- 检查技术决策是否与 spec 冲突、类型和接口是否完整、数据流是否闭合。

### 审批提示

```text
plan.md 已生成。请 review：
- 架构划分是否合理？
- 核心接口定义是否完整？
- 模块间交互是否清晰？
- 技术决策是否认同？

确认后进入任务拆解阶段。
```

等待明确批准后才能进入阶段三。

## 阶段三：任务拆解 -> `task.md`

### 流程

重新阅读已批准的 `spec.md` 和 `plan.md`。列出需要新建、修改和测试的文件，把 plan 中的组件拆成有序、可执行的任务。

每个任务必须是一个聚焦的工作单元，目标工作量约为 2-5 分钟；超过这个范围就继续拆分。每个任务必须写清文件、依赖、具体步骤和验证方式，任务之间的依赖必须形成合法且无环的执行顺序。任务要自包含，即使执行者只读当前任务也不会缺关键细节。

### `task.md` 模板

````markdown
# [标题] Tasks

## 文件清单

| 操作 | 文件 | 职责 |
|------|------|------|
| 新建 | `path/to/file` | ... |
| 修改 | `path/to/file` | ... |
| 测试 | `path/to/file` | ... |

## T1: [任务名]

**文件：** `path/to/file`
**依赖：** 无
**步骤：**
1. ...
2. ...

**验证：** 运行 X，期望看到 Y

## T2: [任务名]

**文件：** `path/to/file`
**依赖：** T1
**步骤：**
1. ...

**验证：** 运行 X，期望看到 Y

## 执行顺序

```text
T1 -> T2 -> T3
             \
T4（可并行） -> T5 -> T6
```
````

### 写作与自检

- plan 中的每个组件至少对应一个任务；文件清单覆盖实现、集成和测试所需文件。
- 每个任务的步骤定位到文件级别，写具体操作，不用“类似 T2”或模糊占位语。
- 每个任务都有“验证”部分，写明运行什么以及期望观察到什么。
- 检查依赖链无循环、存在合法执行顺序、函数名和类型名与 plan 一致。
- 检查没有 `TBD`、`TODO` 或未完成任务。

### 审批提示

```text
task.md 已生成，共 N 个任务。请 review：
- 任务粒度是否合适？
- 依赖关系是否正确？
- 有没有遗漏的实现步骤？

确认后进入验收设计阶段。
```

等待明确批准后才能进入阶段四。

## 阶段四：验收设计 -> `checklist.md`

### 流程

重新阅读已批准的 `spec.md`、`plan.md` 和 `task.md`：

1. 将 spec 的每条验收标准至少转换为一个 checklist 条目。
2. 从 plan 提取模块集成、数据流和架构层面的验证点。
3. 补充编译、单元测试、集成测试和 lint 检查（项目有对应工具时）。
4. 至少设计一个完整的端到端场景，必要时补充边界场景。

### `checklist.md` 模板

```markdown
# [标题] Checklist

> 每一项通过运行代码或观察行为来验证，聚焦系统行为。

## 实现完整性
- [ ] [组件 A] 已实现且可被调用（验证：编译通过）
- [ ] [功能 X] 输出符合预期（验证：用示例输入运行，观察输出）

## 集成
- [ ] [模块 A] 正确调用 [模块 B]（验证：集成测试通过）
- [ ] 所有公开接口至少被一个真实调用方使用（验证：编译 + 全部测试通过）

## 编译与测试
- [ ] 项目编译无错误
- [ ] 所有单元测试通过
- [ ] lint 检查通过（如有配置）

## 端到端场景
- [ ] 场景 1：[用户操作] -> [可观测的预期结果]
- [ ] 场景 2：[边界情况] -> [预期行为]
```

### 写作与自检

- 每项都必须是“做 X，看到 Y”或“运行 X，期望 Y”，并在括号中写验证方式。
- 条目应与实现解耦；重命名文件或移动函数但行为不变时，checklist 仍然有效。
- 验证粒度要对准功能和用户可见行为，不要求逐行读代码。
- 检查 spec 每条 `AC` 都有对应条目；检查可观测性、集成覆盖和至少一个端到端场景。

### 审批提示

```text
checklist.md 已生成。请 review：
- 是否完整覆盖了 spec 的验收标准？
- 每项是否都可以运行或观察验证？
- 端到端场景是否合理？

确认后进入开发阶段。
```

等待明确批准后才能进入阶段五。

## 阶段五：开发

四份文档全部通过审批后，先宣告：

```text
四份文档已全部通过审批，按 task.md 开始开发。
```

然后：

1. 阅读 `task.md` 并创建进度追踪。
2. 按执行顺序逐个完成任务，严格遵循任务步骤。
3. 每个任务或每组逻辑相关任务完成后，立即运行该任务的验证方式。
4. 先取得命令输出、测试结果或可观察行为等证据，再报告任务完成并标记状态。
5. 验证失败时先修复并重新验证，不带着失败进入下一任务。
6. 除非被阻塞，不要自由扩展 task.md 未定义的范围。
7. 每个任务或逻辑相关任务组完成后提交代码，若当前工作流不允许提交，则明确报告这一点而不伪造提交结果。

如果执行遇到阻塞，停在当前任务，说明阻塞原因、已取得的证据和需要用户决定的事项；不要猜测或绕过硬性门控。

## 阶段六：验收

开发完成后阅读 `checklist.md`，逐项执行验证方式并记录实际结果和证据，再标记通过或不通过。

- 失败项要修复后重新验证，并在报告中保留实际失败原因和修复结果。
- 报告实际观察结果，不把预期结果冒充为证据。
- 端到端场景必须走完整用户可见流程。

使用以下报告结构：

````markdown
## 验收报告

### 通过（N/M）
- [x] 条目 1 — 证据：...
- [x] 条目 2 — 证据：...

### 未通过（如有）
- [ ] 条目 3 — 预期：X，实际：Y，修复方案：...

### 端到端
- [x] 场景 1 — 结果：...
````

## 工作原则

- 一次一个问题，优先选择题。
- 逐段呈现，逐段确认；逐份文档，逐份审批。
- 层层递进：spec 只描述行为，plan 负责技术设计，task 负责文件级执行，checklist 负责可观测验收。
- YAGNI：只设计和实现 spec 明确包含的内容。
- 先有证据再下结论：每个任务和每个验收条目都要有实际验证。
- “太简单了”“spec 很明显”“先写代码再补文档”“测试通过就够了”都是跳过流程的危险信号，不能据此放宽硬性门控。
